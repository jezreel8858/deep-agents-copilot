# CLAUDE.md — governanca-ai-reutilizavel

## 1) Objetivo

Este arquivo é a fonte de verdade operacional para o uso de IA em qualquer repositório que adote esta base de governança.

- Escopo desta base: estabelecer governança genérica, desacoplada de domínio e tecnologia.
- Regra de ouro: evitar duplicação de regra entre arquivos de instrução.

## 2) Hierarquia de Instruções

Em caso de conflito, siga esta ordem:

1. System
2. Developer
3. User
4. Arquivos locais deste repositório (`CLAUDE.md`, `.github/*`)

## 3) Regras Normativas (R-001..R-060)

- **R-001 (Escopo)**: altere apenas o que foi solicitado.
- **R-002 (Mudança mínima)**: prefira alterações pequenas, reversíveis e rastreáveis.
- **R-003 (Sem duplicação)**: regra global fica em `CLAUDE.md`; `.github/*` referencia, não copia.
- **R-004 (Rastreabilidade)**: sempre citar caminhos exatos dos arquivos tocados.
- **R-005 (Não inventar catálogo)**: não listar agent/skill inexistente.
- **R-006 (Pré-condições — Roteador)**: vide [`agent-router.agent.md`](.github/agents/agent-router.agent.md) § *Matriz de Decisão: Quando Pedir Contexto*. Regra específica do roteador; não é norma global.
- **R-007 (Decisões explícitas)**: registrar decisões relevantes em bullets curtos.
- **R-008 (Execução obrigatória via context-mode — Think in Code & Zero-Noise Test Policy)**: O uso de `context-mode` MCP (`ctx_execute`, `ctx_execute_file`, `ctx_batch_execute`, `ctx_index`, `ctx_search`) é **100% OBRIGATÓRIO tanto para LEITURAS quanto para MODIFICAÇÃO/CRIAÇÃO de arquivos** SEMPRE que a ferramenta context-mode estiver disponível no ambiente. O processamento de dados e mutações operam no sandbox em código (Think-in-Code), imprimindo apenas o resultado derivado limpo. Ferramentas nativas de editor (`read_file`, `replace_string_in_file`, `insert_edit_into_file`, `create_file`) e comandos de varredura no terminal são **estritamente proibidas quando o context-mode estiver disponível**, sendo rebaixadas a **fallback exclusivo** para quando o servidor MCP context-mode estiver comprovadamente indisponível ou desconectado (`run_in_terminal` em fallback é restrito a comandos de ciclo de vida). **Diretriz Zero-Noise Test Execution**: Comandos de execução de teste no terminal nunca podem ser executados bare; use flags de supressão/filtros ou preferencialmente execução no sandbox `ctx_execute` (ver `.github/skills/terminal-governance/SKILL.md`). **Single-Turn MCP Batching Compulsório & Proibição de MCP Tool Chaining Sequencial no Chat (Smell 2.26)**: É terminantemente proibido encadear chamadas individuais de `ctx_execute` no chat; toda inspeção ou análise múltipla DEVE ser consolidada em chamada única via `ctx_batch_execute` ou script iterativo consolidado em `ctx_execute`. Se o Context Mode falhar, PARE e informe o problema.
- **R-009 (Sem arquivos autônomos)**: nunca crie arquivos de qualquer formato sem solicitação explícita. Se julgar necessário, SOLICITE aprovação ANTES.
- **R-010 (Segurança)**: nunca expor credenciais, tokens ou dados sensíveis.
- **R-011 (Sem overengineering)**: implementar o necessário para a fase atual.
- **R-012 (Clarificação progressiva)**: antes de implementar, avalie se a solicitação tem escopo suficiente. Se ambígua, use `ask_questions` com sugestões pré-preenchidas — nunca pergunte em aberto. Máximo 3 perguntas por ciclo. Não aplique em solicitações simples com intenção clara.
- **R-013 (PT-BR operacional)**: documentação de governança e respostas operacionais em PT-BR.
- **R-014 (Um objetivo por arquivo)**: cada documento deve ter responsabilidade clara.
- **R-015 (Atualização atômica de catálogo)**: alterou governança, atualize os READMEs de catálogo na mesma entrega.
- **R-016 (Evidência objetiva)**: resultados com evidência (`arquivo`, `simbolo`, `comando`) e próximo passo mínimo.
- **R-017 (PT-BR com acentuação correta)**: em arquivos `.md` redigidos em português, use ortografia e acentuação corretas. Evite transliteração ASCII quando o termo exigir acento.
- **R-018 (Planejamento paralelo)**: ao estruturar planos, identifique etapas independentes. Marque com `[P]` paralelo ou `[S]` sequencial. Etapas sem dependência DEVEM ser agrupadas para execução simultânea.
- **R-019 (Busca web proativa com ctx-cache)**: antes de propor solução para cenários de incerteza técnica, siga o fluxo: `ctx_search` no cache primeiro → Tavily se insuficiente → indexar resultado via `ctx_index`. Para docs externos, prefira `ctx_fetch_and_index` (cache 24h nativo). Não use para perguntas sobre o próprio codebase.
- **R-020 (Falha compacta)**: ao reportar erros, use formato 3 linhas — Causa / Local / Ação sugerida. Proibido stack trace completo sem pedido. Máximo 5 erros; resto: `(+N erros similares)`.
- **R-021 (Model Routing Signal)**: avalie o tipo da tarefa antes de agir. Emita sinal visual **antes** de codar quando a tarefa exigir modelo 1× ou superior. MCP tools amplificam modelos menores — use-os antes de escalar. Nunca use modelo pesado para tarefa que modelo leve resolve.
- **R-021.1 (Sinal Adicional de Fan-Out — Model Routing por Volume de Alvos)**: quando uma tarefa de despacho (turno raiz ou agent mutador com `ctx_batch_execute`) envolver **10 ou mais alvos/arquivos/operações homogêneas estimados**, emita o Model Routing Signal (R-021) com motivo explícito de **fan-out alto**, recomendando escalar para modelo 1× ou superior (Sonnet/GPT-5/Gemini Pro conforme disponibilidade) **mesmo que o agent tenha `model:` fixo mais leve declarado no catálogo**. É um sinal de recomendação, não uma trava mecânica de infraestrutura — ver limitação documentada em `.github/skills/context-mode/SKILL.md § 4.1`. Tabela de referência em `.github/copilot-instructions.md § 3`.
- **R-022 (Auto-recuperação do Context Mode)**: quando `ctx_*` falhar com `Not connected`, realize **1 tentativa automática** de recuperação. Após restart, execute 1 health check (`ctx_doctor`) e retome. Se não voltar, PARE e solicite ação manual. Proibido repetir tentativas automáticas.
- **R-023 (MCP Trust Allowlist)**: conecte apenas servidores MCP confiáveis/aprovados; nunca use MCP de origem não verificada.
- **R-024 (MCP Least-Tools)**: mantenha ativas somente as ferramentas MCP necessárias à tarefa corrente.
- **R-025 (MCP Prompt Budget)**: se houver degradação por excesso de tools MCP, reduza a superfície de ferramentas antes de prosseguir.
- **R-026 (Sem código inline em agents/skills/prompts)**: arquivos `.github/agents/*.md`, `.github/skills/*/SKILL.md` e `.github/prompts/*.md` NÃO devem conter blocos de código com implementações > 8 linhas. Código real vai em `snippets/`, `templates/` ou `commands/`, referenciado por caminho ou `source_docs:`.
- **R-027 (Clarificação Obrigatória via ask_questions)**: frente a qualquer ambiguidade, use EXCLUSIVAMENTE `ask_questions` antes de agir. Proibido inferir ou deduzir intenção. A última opção sempre deve ser campo aberto. Sem exceções, ressalvado R-041 (loop controlado do agent `prompt-structuring`, limitado a 5 iterações).
- **R-028 (Estrutura de Resposta — Code Assist Standard)**: ao iniciar qualquer implementação, exiba resumo em 5 seções: **(1)** Resumo da Abordagem; **(2)** Visão Geral dos Componentes; **(3)** Implementação; **(4)** Passos Cruciais; **(5)** Notas Técnicas de Impacto. Para outros perfis de agent (router, analista, operacional), consulte o modelo de 2 camadas (universal + template por perfil) em `.github/skills/agent-contracts/SKILL.md` § 8.
- **R-029 (Postura Senior Engineer)**: **(a)** prefira bullets e tabelas a parágrafos; **(b)** código limpo sem explicações inline; **(c)** elimine introduções genéricas de IA — responda como colega sênior, preciso e focado.
- **R-030 (Checkpoint obrigatório por fase/plano)**: durante `/implement`, ao concluir cada fase (`- [x]`) e ao concluir o plano, execute `/ctx-checkpoint` imediatamente, registrando `lastStep`, `nextStep` e `source` do checkpoint na resposta.
- **R-031 (Plano Auto-Implementável — Zero-Interrupção)**: todo plano aprovado (explícito ou por contexto claro) DEVE ser executado integralmente sem interrupção nem contra-medida do agent. **Pré-voo obrigatório** antes de iniciar: **(a)** Escopo completo — todos os artefatos mapeados e dependências resolvidas; **(b)** Contingências por fase — cada passo com `[fallback: <ação alternativa se falhar>]` inline; **(c)** Critério de falha tolerável — distinguir o que é contornável (warnings, arquivo ausente, tool lenta) do que é bloqueante real; **(d)** Bloqueantes absolutos — único motivo de parada permitido: violação de R-003 (commit autônomo), exposição de credencial (R-010), ou estado de dados irrecuperável detectado. **Formato de contingência por passo:** `[S] Passo X — descrição [fallback: alternativa]`. Ao final, **relatório de execução** (o que foi feito, o que usou fallback, próximo passo) substitui checkpoints intermediários. Proibido pedir confirmação mid-plan.
- **R-032 (Nomeação de documentação)**: todo novo arquivo de documentação `.md` criado deve usar `kebab-case` no nome.
- **R-033 (Sincronização Automática de Documentação Viva & Proibição de Documentação Especulativa)**: Todo agent executor ou de finalização (`specialists`, `feature-developers`, `ui-stylist`, `database-specialist`, `pr-gatekeeper`, `governance-maintainer`) DEVE, ao concluir qualquer alteração técnica relevante (nova rota, nova entidade/modelo, novo componente/padrão visual, migração DDL de banco, novo workflow ou regra arquitetural), **refletir autonomamente** se a entrega impacta a documentação existente do projeto (`docs/`, `README.md`, ADRs, schemas de banco, adapters locais). Se fizer sentido, DEVE atualizar compulsoriamente a documentação existente na mesma entrega como critério de *Definition of Done (DoD)*, sem exigir lembrete manual do usuário. **Proibição Restrita (Anti-Documentação Especulativa)**: permanece terminantemente proibido criar arquivos `.md` novos avulsos, resumos narrativos não solicitados ou tutoriais desconectados da entrega técnica realizada.
- **R-034 (Health Check de Binding Context)**: ao iniciar trabalho em novo repositório com esta base, Copilot DEVE verificar se existem `.github/instructions/README.md` e `.github/projects.local.yaml.example`. Se faltarem: ⚠️ **ALERTAR E DISPARAR AGENT `binding-initializer`** com sequência de `ask_questions` para gerar arquivos customizados. Sem exceções — binding é pré-requisito para descoberta de adapters.
- **R-035 (Terminal sem paginação interativa — Zero Pager Bloqueante)**: NUNCA executar comandos git ou de sistema que abram pager interativo (`less`, `more`, `man`, `git diff` puro, `git log` puro, `git show` puro, `git branch`/`tag` longos) que exijam `q` para sair e travem a sessão indefinidamente em "Processing...". TODO comando git no terminal que produza saída DEVE compulsoriamente incluir flag não-interativa: **SEMPRE usar `git --no-pager <comando>`** (ex.: `git --no-pager diff ...`, `git --no-pager log ...`, `git --no-pager show ...`) OU prefixar inline com `GIT_PAGER=cat git <comando>` OU pipear com `| cat`. O uso de `git diff` puro ou `git log` puro sem `--no-pager` é **TERMINANTEMENTE PROIBIDO E BLOQUEANTE**. Em repositórios de workspace, configurar `git config core.pager cat` como salvaguarda incondicional no nível do Git.
- **R-036 (Identificador Normativo Reservado / Rastreabilidade Histórica)**: número normativo reservado e preservado para assegurar integridade referencial cruzada e rastreabilidade entre versões do catálogo de governança.
- **R-037 (Ponto de Entrada Obrigatório — Agent Router First)**: **SEM EXCEÇÕES**, toda solicitação deve começar com `@agent-router`. Controller routing é o ponto de entrada único para: **(a)** classificação de intenção; **(b)** decisão de rota; **(c)** prevenção de implementação direta sem triagem. O roteador delega para downstream (bug-triage, test-strategy, refactor-planner, docs-engineer, deep-search, tech-solution-architect) conforme necessidade. Bypass de @agent-router é violação de governança. Proibido implementar sem passar por triagem. **Salvaguarda Anti-Duplicação de Subagente**: Quando o `@agent-router` emitir o bloco de decisão (`Delegado: @<agent>`), o Orquestrador Raiz despacha o agent delegado UMA ÚNICA VEZ. Se por qualquer anomalia a resposta do subagente já contiver o resultado de execução concluída do downstream (`Resultado do @<agent>:`), o Orquestrador NUNCA deve re-invocar o mesmo agent.
- **R-038 (Genericidade Obrigatória em Governança)**: Toda documentação de governança criada em `.github/` (agents, skills, prompts, copilot-instructions) **DEVE ser genérica**, desacoplada de: **(a)** projetos específicos; **(b)** tecnologias exclusivas; **(c)** convenções de domínio particulares. Convencionalidades, adapters e exemplos concretos **PERTENCEM EXCLUSIVAMENTE A** `.github/instructions/*.instructions.md` (adapters) ou `.github/instructions/` (contexto de binding). Se uma regra de governança referencia projeto, domínio ou tech específica, é violação de R-038. Teste: substituir nome de projeto/tecnologia por `[PROJETO]` ou `[TECH]` — se deixar de fazer sentido, está muito específica para governança global.
- **R-039 (Diagramas em Markdown com Mermaid)**: Todo diagrama incorporado em arquivo `.md` **DEVE usar Mermaid** (sintaxe nativa de blocos code com linguagem `mermaid`). Razões: **(a)** versionabilidade — diagramas vivem no Git, não em binários; **(b)** portabilidade — renderização nativa em GitHub, GitLab, Notion e ferramentas de IA; **(c)** manutenibilidade — patches e reviews sem ferramentas específicas. Proibido: imagens PNG/SVG geradas externamente, Visio, Lucidchart embarcados. Se precisar de estilo avançado, use plugins Mermaid ou refatore para simplificar.
- **R-040 (Grafo de Roteamento como Fonte de Verdade)**: O roteamento de agents **DEVE ser declarado como dado estruturado** (ex.: `.github/agents/routing-graph.yaml` com nós, arestas, thresholds e política de cascata). A Decision Tree em prosa de qualquer agent-router é **documentação derivada** — não fonte única. Toda nova rota ou agente adicionado ao ecossistema exige: **(a)** entrada no grafo estruturado; **(b)** atualização da Decision Tree (derivada); **(c)** novo caso de teste em `.github/agents/evals/casos-roteamento.yaml` (equivalente ao R-015 para evals). Threshold de confiança para cada rota deve ser declarado explicitamente no grafo e reportado no output do router.
- **R-041 (Exceção de Loop Controlado — Agent `prompt-structuring`, Autonomia Delimitada em 3 Tiers & Fast-Path Determinístico)**: por exceção formal a R-011 (sem overengineering), R-012 (clarificação progressiva, máx. 3 perguntas/ciclo) e R-027 (proibição de loop em `ask_questions`), o agent `prompt-structuring` é o **ÚNICO** agent do catálogo autorizado a operar em loop de auto-refinamento de prompt. Opera sob o modelo de **Autonomia Delimitada (Bounded Autonomy)** em 3 Tiers para mitigar anti-padrões de mercado em sistemas multi-agentes (*Approval Fatigue*, *Agency Stripping* e *Latency Tax*):
  - **Tier 1 (Fast-Path Determinístico — Latência Zero)**: solicitações com intenção operacional evidente — **(1) Bug / Defeito / Layout / Runtime Error** (para `@bug-triage`); **(2) Refatoração Estrutural com alvo definido** (para `@refactor-planner`); **(3) Análise Técnica / Grafo / Auditoria direta** (para especialista analítico) — **DEVEM acionar o Fast-Path bypass**, ingressando imediatamente na Etapa 1 do workflow canônico (R-050) sem passar por `@prompt-structuring`.
  - **Tier 2 (Gate Pattern / "Prepare, Don't Submit" — Confirmação de 1-Clique)**: tarefas médias ou features com alvo delimitado — o estruturador gera o prompt canônico `<task>/<context>/<constraints>/<output_format>` em **1 turno único** e apresenta preview estruturado para confirmação humana rápida via `ask_questions` antes do despacho, prevenindo fadiga de aprovação.
  - **Tier 3 (Interactive Loop / Elicitação Multi-Turno)**: reservado para pedidos ambíguos, conceituais ou requisitos abertos. Regras do loop: **(a)** limite rígido `loop_count <= 5` — interrompido compulsoriamente na 5ª iteração; **(b)** no máximo 1 pergunta objetiva com opções por iteração via `ask_questions`; **(c)** encerramento antecipado assim que o prompt atingir completude; **(d)** retorno SEMPRE ao `@agent-router`.
  - **Fronteira Estrita Problem Space vs Solution Space (Anti-Agency Stripping)**: o `prompt-structuring` delimita exclusivamente o *Quê*, requisitos funcionais, não-escopo, DoD e batching R-046. É **terminantemente proibido** prescrever código, algoritmos ou decisões de arquitetura interna, que pertencem aos especialistas de stack.
- **R-042 (Re-triagem Obrigatória por Turno — Anti Sticky-Session)**: R-037 ("toda solicitação começa em `@agent-router`") aplica-se a **cada novo turno do usuário**, não apenas ao primeiro. Todo agent downstream ativo opera em `task_mode` e deve checar deriva de intenção a cada nova mensagem contra seu **Não-Escopo** declarado. **Critério objetivo de deriva** (qualquer um): **(a)** mudança de verbo de ação (elicitar→implementar, revisar→codar, analisar→corrigir, planejar→executar) **quando o agent ativo não cobre implementação** (ex.: `tech-solution-architect`, `bug-triage`, `requirements-analyst`, `test-strategy`, `deep-search`); **(b)** menção a stack/artefato fora da matriz de competência do agent ativo (ex.: pedir código Angular enquanto `@spring-boot-router` está ativo); **(c)** pedido explícito de execução/código quando o agent é estritamente read-only/advisory. **Nota sobre Specialists e Encerramento de Ciclo (Anti Sticky-Agent)**: `angular-router`, `spring-boot-router` e `spring-reactive-router` (e os especialistas em suas respectivas pastas) têm perfil híbrido (Advisory + Implementação). Pedir refinamento ou continuação direta *durante uma tarefa/etapa em andamento* dentro do mesmo domínio de stack não é deriva; **contudo, ao concluir a tarefa/workflow ou diante de uma nova solicitação/problema, o agente DEVE devolver o controle ao `@agent-router`** (R-052). NUNCA reter a sessão para um novo ciclo de desenvolvimento apenas por ser da mesma stack. **Ação obrigatória ao detectar deriva**: handoff imediato de retorno para `@agent-router` (payload do schema `handoff-governance` § 2.1, com `motivo: "deriva_de_intencao"`) — **nunca prosseguir silenciosamente fora do escopo**. Todo `.agent.md` deve declarar seção **"Retorno ao Router"** com o gatilho específico de deriva (atualização atômica conforme R-015). O `agent-router` declara `Agente Ativo: <nome>` em toda resposta para tornar a re-triagem auditável. Arestas de retorno universais (`de: <qualquer downstream> → para: agent-router`, condição `intent_drift_detected`) são declaradas em `.github/agents/routing-graph.yaml` (R-040). **Exceção de ação in-scope**: mudança de verbo de ação NÃO constitui deriva de intenção se a ação solicitada já constar expressamente na seção "Quando Delegar" do agent atualmente ativo (ex.: `tech-solution-architect` já delega pesquisa externa a `deep-search` — logo pedir pesquisa web com `tech-solution-architect` ativo é sub-tarefa in-scope, não deriva). Nesse caso, o router devolve o controle ao agent ativo (sem re-triagem completa). **Protocolo de Retorno Lateral / Call Stack (`call_type: "subroutine"`)**: quando um agent invoca outro como sub-rotina com `origem_contexto.call_type: "subroutine"` e `origem_contexto.return_to_parent: true`, o agent receptor (ex.: `@deep-search`) opera como sub-rotina delimitada e DEVE, ao concluir sua análise ou síntese, invocar `run_subagent(agentName: parent_agent, ...)` devolvendo os dados diretamente ao agent solicitante, em vez de finalizar no chat ou devolver ao `@agent-router` por falsa deriva. **Pré-requisito estrutural (tooling baseline)**: o handoff de retorno só é efetivo se **executado** via tool `run_subagent` (`agentName: "agent-router"`) — descrever o handoff apenas em texto/markdown não cumpre R-042. Por isso, `run_subagent` é **obrigatório e bloqueante** no frontmatter `tools:` de TODO agent do catálogo, incluindo os templates-base (`templates/research-agent.md`, `templates/operational-agent.md`); `agent-factory` valida essa regra em toda criação/revisão (baseline detalhado em `agent-contracts/SKILL.md` § 9). **Visibilidade de fluxo (banner obrigatório)**: para que R-042 seja auditável turno a turno (não apenas no turno em que `@agent-router` responde), **TODO agent — não apenas o `agent-router` — declara `Agente Ativo: <name>` como a primeira linha de toda resposta**, mesmo quando o agent apenas continua respondendo em `task_mode` sem handoff neste turno; quando a resposta é resultado de handoff/re-triagem recebido, uma segunda linha declara a transição (`Handoff: <origem> → <destino> (motivo: ...)`), equivalente ao `HandoffOutputItem` do OpenAI Agents SDK e ao campo `active_agent` streamado pelo LangGraph (padrão de mercado consolidado — detalhes em `agent-contracts/SKILL.md` § 0). Em seguida, o agent declara `Skills Carregadas: <skill-1>, <skill-2>, ...` (nomes curtos das skills efetivamente consultadas/pre-fetched nesta resposta, conforme `source_docs:`/`skills:` do próprio frontmatter — ou `nenhuma (apenas regras globais)` quando aplicável), dando visibilidade explícita da base de conhecimento ativa a cada turno. **Rastreabilidade Estruturada Auxiliar (opcional / context-mode MCP)**: quando houver necessidade de persistir o rastro de delegações além da janela de contexto ou entre sessões, o agent delegante PODE, na mesma resposta (convenção single-turn), indexar o `handoff_payload` (schema `handoff-governance` v1.1, campo opcional `roteamento_grafo`) via `ctx_index(source: "handoff-telemetry", content: ...)`. Esta camada é estritamente AUXILIAR e assíncrona — a leitura via `ctx_search` NÃO deve ser executada como pré-requisito bloqueante antes da triagem de cada novo turno do `@agent-router`, preservando a baixa latência do fluxo. O banner `Agente Ativo:`/`Handoff:` permanece a fonte PRIMÁRIA e obrigatória de visibilidade — nunca é substituído ou deprecado por este mecanismo. A obrigação de re-triagem aplica-se mesmo quando não há agent ativo residente (ex.: logo após conclusão de um workflow anterior) — a ausência de agent ativo NÃO suspende R-037; ver R-063.
- **R-043 (Local Overlay Pattern — Desacoplamento Total de Projetos e Adapters Locais)**: bindings de projeto (`projetos:`) e adapters gerados automaticamente por `adapter-generator` são dados **LOCAIS/PRIVADOS de cada desenvolvedor** e **NUNCA** podem ser escritos no repositório de governança compartilhado/commitado. **Localização obrigatória**: `.github/projects.local.yaml` (overlay de projetos) e `.github/instructions/local/` (adapters por-projeto) — ambos declarados em `.gitignore`, nunca tocados por `git add`/commit de rotina. O repositório mantém adapters genéricos em `.github/instructions/*.instructions.md` (com applyTo nativo) e documentados em `.github/instructions/README.md`. **Template rastreado**: `.github/projects.local.yaml.example` (sem dados reais) é commitado como schema de referência; cada desenvolvedor copia para `projects.local.yaml` (análogo a `.env`/`.env.example`). **Regra de leitura (merge em memória)**: todo agent/prompt que precisa da lista de projetos DEVE ler `projects.local.yaml` (se existir) e mesclar em memória — nunca escrever entrada de projeto de volta no arquivo compartilhado. **Regra de escrita**: `/add-project-context` e `adapter-generator` escrevem exclusivamente em `projects.local.yaml` e `.github/instructions/local/`; `/del-project-context` remove exclusivamente dali. **Defesa em profundidade**: hook `git` em `.githooks/pre-commit` bloqueia commit que introduza `projetos:` não-vazio em catálogos compartilhados ou qualquer arquivo staged sob `.github/instructions/local/` — protege contra `git add -f` acidental. Motivo: evitar que um `git commit`/`push` de rotina suba nomes/caminhos de projetos privados para o repositório de governança compartilhado.
- **R-044 (Anonimização Obrigatória de Evidência de Análise Real)**: agents que **analisam repositórios reais do usuário** (ex.: `code-knowledge-graph`, `business-rules-extractor`, `context-builder`, `project-scanner`) frequentemente produzem "evidência real" (números de validação, nomes de classe/método/namespace, caminhos de arquivo, nomes de repositório) como prova de funcionamento. - **R-053 (Execution Gate Independente de Modelo — Banner-Antes-de-Mutação, não-negociável)**: Modelos de custo médio/alto tendem a "correr para a solução" e pular diretamente para tool calls mutativas (`insert_edit_into_file`, `replace_string_in_file`, `create_file`, `run_in_terminal` com efeito colateral) assim que formulam um plano internamente — este é o padrão de desvio de pipeline mais recorrente observado (independentemente da causa exata do agent estar analisando/implementando), e sua mitigação **NÃO pode depender da "boa vontade" ou capacidade de auto-disciplina do modelo ativo no picker**. Regra estrutural obrigatória, verificável mecanicamente turno a turno:
  **(a) Sequência bloqueante**: Em qualquer turno onde o agent pretenda invocar uma tool mutativa dentro de um workflow canônico (R-050) ativo, o texto de resposta DEVE conter, **antes da primeira invocação de tool mutativa do turno**, o banner `Agente Ativo: <nome>` e, se a etapa mudou desde a última mensagem do próprio agent, o bloco `### 🗺️ Pipeline de Execução do Workflow`. Não basta declarar o handoff *depois*, no resumo final — a ordem de emissão importa tanto quanto o conteúdo (R-048 já exige isso para handoffs pós-`ask_questions`; R-053 generaliza a exigência para toda mutação dentro de qualquer workflow, não apenas pós-clarificação).
  **(b) Checkpoint humano não é satisfeito por continuação genérica**: Uma resposta curta e genérica do usuário ("prossiga", "continue", "ok", clique em sugestão automática de continuação) **nunca** substitui uma aprovação explícita de itens específicos sinalizados como pendentes/divergentes/ambíguos (`⚠️`, `[⏳ PENDENTE]`) em um Checkpoint Humano declarado (Estados `*b` dos workflows em `workflows.md`). O agente deve reapresentar as opções concretas via `ask_questions` antes de agir sobre esses itens — nunca decidir unilateralmente com base em uma continuação vaga.
  **(c) Proibição de fallback manual silencioso após falha de tool determinístico**: Se um tool determinístico obrigatório do workflow (ex.: `@code-knowledge-graph`/`@optave/codegraph`) falhar, retornar erro ou timeout, é proibido compensar silenciosamente com varredura manual (`list_dir`, `grep`/`grep_search` em massa, leitura sequencial de dezenas de arquivos) sob a mesma identidade de agente — a única ação permitida é retry do próprio tool determinístico ou declaração explícita da falha (3 linhas: Causa/Local/Ação sugerida) seguida de `ask_questions`.
  **(d) Auto-auditoria obrigatória em caso de detecção tardia**: Se o próprio agent perceber, em qualquer ponto da conversa, que já executou tool calls mutativas sem ter cumprido (a)/(b)/(c) no mesmo turno, ele DEVE parar imediatamente, rodar uma auditoria factual do estado real dos arquivos afetados (nunca confiar em memória — usar `git diff`/`git status`/releitura do arquivo), declarar o desvio explicitamente ao usuário e só então retomar seguindo a sequência correta a partir do checkpoint que faltou — nunca simplesmente seguir em frente "como se nada tivesse acontecido".

- **R-051 (Proteção Anti-Corrupção em Edição de Arquivo Único Grande/Estruturado e Markdown com Âncoras Repetidas)**: Antes de editar QUALQUER arquivo — mesmo um único arquivo, fora do escopo de R-046 (que trata de lote multi-arquivo) — se o arquivo-alvo tiver mais de 200 linhas, OU extensão `.yaml`/`.yml`/`.json` (sintaxe sensível a indentação), OU for **Markdown estruturado** (`.agent.md`, `.instructions.md`, arquivos de governança `.md` com frontmatter YAML, seções com títulos parecidos ou tabelas repetitivas), OU for consumido diretamente por testes automatizados/CI:
  **(a) Proibição de Ferramentas de Risco**: `insert_edit_into_file` é **ANTI-PADRÃO BLOQUEANTE** nesses arquivos (risco comprovado de truncamento silencioso).
  **(b) Proibição de Confiança Cega em `replace_string_in_file` e Fallback Fuzzy**: `replace_string_in_file` utiliza heurísticas de correspondência aproximada quando a âncora não é estritamente unívoca; em Markdown estruturado e tabelas, isso causa corrupção catastrófica (apagamento de frontmatter e cabeçalhos ou duplicação de linhas de tabela — incidente real documentado em `code-knowledge-graph.agent.md`).
  **(c) Verificação de Unicidade de Âncora (Padrão de Edição Segura Verificada)**: O agent DEVE seguir o padrão definido em `efficient-batch-code-modification/SKILL.md` § 5 (ler o arquivo inteiro → contar ocorrências exatas do texto-âncora em memória → abortar compulsoriamente se `count !== 1` → escrever somente se seguro → reler do disco para confirmar). Se houver risco de colisão de âncoras repetidas ou em arquivos estruturados, o uso de `ctx_execute` com all-or-nothing write é **MANDATÓRIO**.
  **(d) Validação Pós-Escrita de Integridade Estrutural**: O agent NUNCA deve confiar na mensagem de sucesso retornada pela tool; deve reler/validar o estado real do arquivo confirmando que seções essenciais (frontmatter `---`, `# Título`, seções canônicas) e a contagem de linhas permanecem íntegras antes de considerar a edição concluída. Incidentes de origem documentados em `efficient-batch-code-modification/SKILL.md` § 5 e `governance-audit-patterns/SKILL.md` Smell 2.16.
- **R-054 (Governança Estrita de Routers — Tooling Least Privilege, Zero Discovery e Delegação Plana Obrigatória)**: Todo agent com perfil de roteador (central `@agent-router` ou supervisores hierárquicos de domínio `*-router`) atua exclusivamente como classificador semântico de intenção e despachante puro, devendo cumprir compulsoriamente os 3 pilares:
  **(a) Least Privilege de Ferramentas (Invariante Universal)**: O frontmatter `tools:` é restrito exclusivamente ao baseline canônico de roteamento (`read_file`, `file_search`, `grep_search`, `list_dir`, `ask_questions`, `run_subagent`, `context-mode/ctx_search`). É **terminantemente proibido** dotar qualquer router de ferramentas mutativas (`insert_edit_into_file`, `create_file`, `replace_string_in_file`, `apply_patch`), ferramentas de execução/sandbox (`context-mode/ctx_execute`, `context-mode/ctx_execute_file`, `context-mode/ctx_batch_execute`, `run_in_terminal`) ou comandos de IDE.
  **(b) Zero Pre-Routing Discovery (Anti-Overthinking Router)**: O router NÃO executa tool calls exploratórias (leitura de código, varredura de diretórios, scripts de sandbox) para analisar ou diagnosticar a solicitação do usuário antes de rotear, mesmo diante de arquivos anexados (`#file:...`). A classificação baseia-se estritamente na intenção do prompt e na categoria da tarefa. A inspeção técnica profunda cabe exclusivamente ao especialista downstream delegado. É igualmente terminantemente proibido ao router executar ferramentas de busca ou leitura em runtime para inspecionar catalog.yaml ou *.agent.md em busca de modelos de subagentes (a resolução de modelo é estática/melhor esforço — R-054).
  **(c) Delegação Plana Universal (Anti-Aninhamento / Smell 2.20 / Smell 2.23)**: O router encerra seu turno emitindo o bloco declarativo de decisão (`Agente Ativo`, `Delegado: @<agent>`, `Pipeline de Execução`) para que o Orquestrador Raiz despache o especialista em nível plano. É **terminantemente proibido** ao router invocar subagentes downstream executores ou especialistas internamente via `run_subagent` (com exceção estrita de `@prompt-structuring` R-041 e `@binding-initializer` R-034 no router central).
- **R-055 (Portão de Reúso e Generalização Sistêmica em Governança — Anti-Silo Fix)**: Toda solicitação de melhoria, ajuste, novo padrão ou correção técnica que incida sobre agents, prompts ou skills DEVE obrigatoriamente passar pelo crivo do *Systemic Reuse Gate* como prioridade máxima no `WORKFLOW-GOVERNANCE-MAINTENANCE`. É **terminantemente proibido** aos agentes de governança (`@agent-auditor`, `@governance-factory`, `@governance-maintainer`) aplicar correções isoladas (em silo / *one-off fixes*) quando o problema ou diretriz for de natureza arquitetural ou extensível. O agente DEVE avaliar e responder compulsoriamente a 3 perguntas antes da execução:
  **(a) Q1 (Impacto Horizontal / Peers)**: *Esta melhoria ou correção se aplica a outros artefatos do mesmo perfil, camada ou família (ex.: outros routers, outros testers, outros advisors)?* Se sim, o escopo da entrega DEVE ser expandido em lote único (*Single-Turn Batching*, R-046) para cobrir todos os artefatos análogos na mesma entrega.
  **(b) Q2 (Prevenção Futura / Templates)**: *O template canônico em `templates/` (`router-agent.md`, `operational-agent.md`, etc.) reflete essa nova exigência?* Se não, o template correspondente DEVE ser atualizado compulsoriamente para que futuros artefatos gerados pelo `@governance-factory` já nasçam em conformidade.
  **(c) Q3 (Blindagem por Teste / Quality Gate)**: *A suíte determinística em `tests/governance_audit/` já valida essa regra?* Se não, uma asserção ou teste específico no pytest DEVE ser criado ou expandido para garantir não-regressão contínua.
- **R-056 (Precedência Mandatória e 100% Obrigatória de Context Mode em Leitura e Modificação de Arquivos — Anti-Editor Tool Sprawl)**: Todo agent com capacidade de escrita ou leitura DEVE obrigatoriamente utilizar `context-mode` (`ctx_execute`, `ctx_execute_file`, `ctx_batch_execute`, `ctx_index`, `ctx_search`):
  **(a) Obrigatoriedade Não-Negociável**: O uso de context-mode é **100% OBRIGATÓRIO tanto para LEITURAS quanto para MODIFICAÇÃO/CRIAÇÃO de arquivos** SEMPRE que a ferramenta context-mode estiver disponível no ambiente, com escrita all-or-nothing verificada (R-051).
  **(b) Proibição de Ferramentas de Editor e Fallback Exclusivo**: Ferramentas nativas de editor (`read_file`, `replace_string_in_file`, `insert_edit_into_file`, `create_file`) e comandos de varredura no terminal são **estritamente proibidas quando o context-mode estiver disponível**, sendo rebaixadas a **fallback exclusivo** única e exclusivamente para quando o servidor MCP context-mode estiver comprovadamente indisponível ou desconectado.
  **(c) Herança Compulsória**: Todo novo agent do `@governance-factory` herda compulsoriamente a cláusula de 100% context-mode e a skill `efficient-batch-code-modification`.
  **(d) Proibição de MCP Tool Chaining Sequencial & Single-Turn MCP Batching (Smell 2.26)**: Proibido disparar chamadas unitárias sucessivas de `ctx_execute` no chat; unifique múltiplos alvos em chamada única via `ctx_batch_execute` ou script síncrono consolidado em `ctx_execute`.
- **R-057 (Proibição Estrita de Terceirização de Edição Manual ao Usuário por Agentes Analíticos / Read-Only — Anti-Manual User Delegation & Automated Workflow Continuity)**: Agentes analíticos, supervisores, auditores, advisors ou com perfil read-only que não possuem ferramentas de mutação (`insert_edit_into_file`, `create_file`) são **terminantemente proibidos** de emitir instruções de alteração manual de código ou arquivos para o usuário ("edite você mesmo no arquivo X", "não possuo ferramentas de edição, faça a alteração manual da linha Y por Z").
  **(a) Continuidade Automática de Workflow**: Ao concluir sua análise técnica, diagnóstico ou auditoria e identificar a necessidade de alterações no código ou na governança, o agente DEVE compulsoriamente avançar para a próxima etapa do respectivo workflow canônico (R-050) ou delegar a execução ao agente executor/fixer competente do ecossistema (Flat Delegation / handoff R-042/R-047).
  **(b) Erradicação do Beco Sem Saída (Anti-Dead-End)**: O encerramento de resposta com meras instruções descritivas de edição transferindo trabalho manual ao usuário constitui violação de R-047 e Smell 2.25. Agentes analíticos devem emitir seu parecer/diagnóstico estruturado e disparar a transição determinística para o executor (ex.: `@governance-maintainer`, `@bug-fixer`, `@feature-developer`).
  **(c) Herança Compulsória em Contratos e Templates**: Todo agente analítico ou read-only existente e os templates canônicos (`research-agent.md`, `agent-template.md`, `router-agent.md`) devem conter explicitamente no bloco CRÍTICO de Não-Escopo a vedação de transferir edições ao usuário sob pretexto de falta de ferramentas.
- **R-058 (Blueprint Técnico e Decomposição Obrigatórios em Features Complexas — Anti-Premature Implementation Bypass & Anti-Gap Dumping)**: Toda solicitação de nova funcionalidade que envolva: **(1)** criação ou evolução de schema de banco de dados ou persistência (incluindo Firestore, MongoDB, Supabase ou RDBMS); **(2)** máquina de estados finita com 3 ou mais transições/ciclos de aprovação; **(3)** concorrência, locks ou operações com transações atômicas; OU **(4)** integração com infraestrutura de notificações push, plugins nativos de dispositivo ou matriz de regras de autorização/segurança, **NUNCA deve ser despachada diretamente para os Domain Routers ou especialistas de código** (`@angular-router`, `@spring-boot-router`, `feature-developer`, etc.).
  **(a) Passagem Obrigatória por `@tech-solution-architect`**: O `@agent-router` DEVE compulsoriamente encaminhar a solicitação para o **Estado 3 do `WORKFLOW-FEATURE-DEVELOPMENT` (`@tech-solution-architect`)** para elaboração do Technical Blueprint formal (modelagem de schema, tabela de transição de estados, mitigação de concorrência e particionamento de tarefas via Context Firewall) e submissão ao Checkpoint Humano 3b (`ask_questions`) ANTES de qualquer geração de código.
  **(b) Decomposição em Subtasks via `@feature-planner`**: Após a aprovação do Blueprint Técnico, se a feature contiver 3 ou mais frentes de trabalho ou fluxos dependentes (ex.: Modelo + UI + Push + Testes), a decomposição em subtasks sequenciais `[S]` e paralelas `[P]` com Definition of Done granular cabe ao `@feature-planner` (Estado 3c / 4), em vez de deixar a ordem de execução no improviso do implementador.
  **(c) Proibição Estrita de Despejo de Lacunas Arquiteturais (Anti-Gap Dumping / Smell 2.27)**: É terminantemente proibido ao `@agent-router` identificar lacunas arquiteturais em seu raciocínio (ex.: matriz de papéis/permissões, formato de payload em banco, escopo de tokens de push notification) e despejá-las no bloco "Lacunas para handoff" para que o especialista de implementação resolva no improviso durante a codificação. A existência de qualquer lacuna de schema, autorização ou infraestrutura impõe deterministicamente o roteamento para `@tech-solution-architect`.
  **(d) Proibição de Roteador Atuar como Planejador Inline (R-054)**: É expressamente vedado ao `@agent-router` inventar listas arbitrárias de sub-etapas técnicas ou cronogramas de implementação linear no chat para substituir a esteira canônica de arquitetura e planejamento.

- **R-059 (Regra do Limiar >= 2 e Protocolo Plan-Then-Batch Global — Anti-MCP Tool Chaining & Anti-Miopia Reativa — Smell 2.26 & Smell 2.13)**:
  **(a) Regra do Limiar >= 2 (inegociável)**: Se a tarefa exigir inspecionar, ler, editar ou executar 2 ou mais alvos/comandos, é TERMINANTEMENTE PROIBIDO disparar `ctx_execute` isolado por alvo em chamadas sucessivas. É OBRIGATÓRIO consolidar tudo em chamada única via `ctx_batch_execute(commands, queries)` ou script iterativo único em `ctx_execute`.
  **(b) Protocolo Plan-Then-Batch**: (1) *ENUMERAR* internamente todos os alvos antes de qualquer tool call; (2) *CONSOLIDAR* tudo em payload única se houver >= 2 itens; (3) *DESPACHAR* em chamada única por fase; (4) *Comandos curtos não suspendem a regra*: prompts como "prosseguir" mantêm o rigor estrito de context-mode e batching.
  **(c) Circuit Breaker de Tool-Chaining Sequencial**: Se 2 chamadas unitárias de `ctx_execute`/`ctx_execute_file` ocorrerem consecutivamente sem `ctx_batch_execute`, o agente deve interromper a 3ª chamada e reconsolidar compulsoriamente os alvos pendentes em lote único com `cwd` explícito (detalhes em `.github/skills/context-mode/SKILL.md` § 4.1-4.2).
  **(d) Remissão Normativa**: Detalhamento em `.github/copilot-instructions.md` § 2.1 e `.github/skills/efficient-batch-code-modification/SKILL.md`.

- **R-060 (Teto Rígido de Tool Turns (≤ 5), Warm Start Compulsório e Consolidação de Queries em Lote — Anti-Token Debt & Anti-Turn Chaining)**:
  **(a) Teto Rígido de Tool Turns (≤ 5 por ciclo de execução)**: Orçamento estrito de no máximo 5 turnos de ferramentas por ciclo (Turno 1: Warm Start / Batch Gather; Turno 2: Execução em lote; Turno 3: Validação consolidada; Turnos 4-5: Síntese final ou Circuit Breaker compulsório no 4º turno para conter dívida de tokens O(N²)).
  **(b) Warm Start Compulsório (Build-if-Missing & Silent Initialization)**: Caches e índices locais (ex.: `.codegraph/graph.db`) devem ser verificados e construídos silenciosamente no turno inicial (build-if-missing) antes de queries, vedando falhas por cold start.
  **(c) Consolidação de Queries em Lote (Batch Querying & Edge Truncation)**: Consultas a grafos e buscas devem ser agrupadas via chamadas em lote (`batch_query`, `ctx_batch_execute`), aplicando Edge Truncation e destilação semântica no sandbox (Think-in-Code) sem vazar árvores brutas no chat.
  **(d) Remissão Normativa**: Detalhamento em `.github/copilot-instructions.md` § 2 e skills `terminal-governance`, `codegraph-optave-usage` e `efficient-batch-code-modification`.

- **R-061 (Diagnóstico de Harness-vs-Modelo e Poda Anti-Bloat de Instrução — Harness Engineering)**: Consolida heurísticas de mercado 2026 (Matt Pocock/AI Hero; HumanLayer) para diagnóstico de comportamento de agent e minimalismo de arquivos de instrução:
  **(a) Diagnóstico Harness-Antes-de-Modelo**: Diante de comportamento anômalo de um agent (recusa, alucinação aparente, ação não executada), o agente/analista DEVE descartar 4 hipóteses de harness — tools ativas, instrução/system-prompt carregado, permissões/hooks e volume de contexto acumulado — **antes** de concluir limitação do modelo subjacente ou escalar via Model Routing Signal (R-021).
  **(b) Heurística da Zona Inteligente (~100k tokens)**: Sessões que acumulam ~100k tokens de contexto ativo (histórico + arquivos + saídas de tool) devem ser tratadas como candidatas a reset com handoff sucinto (`handoff-governance`) em vez de compactação indefinida do histórico — independentemente do tamanho anunciado da janela de contexto do modelo.
  **(c) Minimalismo e Progressive Disclosure em Instrução-Raiz**: Arquivos-raiz de instrução (`CLAUDE.md`, `AGENTS.md`, `.github/copilot-instructions.md`) devem conter apenas o que é verdadeiramente aplicável a toda tarefa; regra específica de sub-domínio pertence a adapter/instruction separado (progressive disclosure), nunca despejada no arquivo-raiz.
  **(d) Poda Cirúrgica Anti-Bloat ("Delete e Observe")**: Suspeita de degradação por acúmulo de instrução redundante/vaga é investigada removendo cirurgicamente o excesso (nunca silenciosamente) e observando normalização — vedado remover qualquer regra normativa (R-xxx) sem aprovação humana explícita (`ask_questions`).
  **(e) Remissão Normativa**: Detalhamento operacional, checklist e exemplos em `.github/skills/harness-engineering-patterns/SKILL.md`.

- **R-062 (Zero Impersonation pelo Orquestrador Raiz — Anti Root-Agent-Impersonation)**: É TERMINANTEMENTE PROIBIDO ao modelo do turno raiz (antes de qualquer `run_subagent`) ler, abrir, resumir ou parafrasear o conteúdo de qualquer arquivo `.github/agents/**/*.agent.md` (de qualquer agent que não seja o próprio `agent-router`) com o intuito de executar aquele papel diretamente no chat raiz, simulando o comportamento do agent sem invocá-lo de fato.
  **(a) Exceção Explícita de Roteamento**: `agent-router.agent.md`, `.github/agents/catalog.yaml` e `.github/agents/routing-graph.yaml` podem ser consultados exclusivamente para fins de roteamento/despacho (classificação de intenção e escolha de rota), nunca para "aprender" e simular o comportamento de um agent específico.
  **(b) Única Forma Válida de Ação**: A única forma válida de "agir como" qualquer agent do catálogo é invocá-lo de fato via `run_subagent`; ler o arquivo `.agent.md` de um especialista e responder no papel dele no chat raiz é impersonação e viola R-037/R-042/R-050/R-054.
  **(c) Fechamento da Brecha de "Exceção de Ação In-Scope" (R-042)**: Comandos diretos citando `@nome-do-agent`, pedidos que citam nome de agent, ou solicitações aparentemente simples/curtas NÃO isentam da passagem obrigatória pelo `@agent-router` primeiro nem autorizam impersonação.
  **(d) Regra Agnóstica de Modelo**: Aplica-se independentemente do modelo usado no turno raiz (Claude, GPT, Gemini etc.).
  **(e) Enforcement**: Validado por `tests/governance_audit/test_root_agent_impersonation_governance.py`.

- **R-063 (Zero Execução Direta pelo Orquestrador Raiz sem Router — Anti Silent Bypass)**: É TERMINANTEMENTE PROIBIDO ao modelo do turno raiz executar diretamente qualquer tool genérica (terminal, `read_file`, `grep`, edição, listagem de diretório) em resposta a um novo pedido do usuário — inclusive quando esse pedido não cita nome de agent algum e inclusive quando não há agent ativo residente por o workflow anterior ter sido declarado concluído (R-052) — sem antes invocar `@agent-router` via `run_subagent`.
  **(a) A ausência de um agent ativo residente NUNCA constitui licença implícita para ação direta; pelo contrário, é precisamente o gatilho que exige nova triagem completa (R-037/R-042).**
  **(b) Pedidos genéricos e informais ("revise as alterações", "verifica isso", "dá uma olhada") não são exceção — são a variante mais comum deste bypass e devem ser tratados como qualquer outra solicitação sujeita a R-037.**
  **(c) Regra agnóstica de modelo (Claude, GPT, Gemini etc.).**
  **(d) Enforcement**: `tests/governance_audit/test_root_orchestrator_silent_execution_governance.py`.

           ↓
    Existe agent ativo de turno anterior? (R-042)
           ├─ Não (1º turno) ────────────────────────────────────────────────────────┐
           └─ Sim -> checar deriva de intenção                                       │
                (verbo de ação | stack fora de                                       │

                ├─ Sem deriva -> devolve ao agent ativo (sem re-rotear)              │
                └─ Deriva detectada (handoff motivo: "deriva_de_intencao") ──────────┤
                                                                                     ↓
                         [CLASSIFICAÇÃO DE WORKFLOW & FAST-PATH (R-041/R-050)]
                                ├────────────────────────────────────────┐
                                │ FAST-PATH DETERMINÍSTICO               │ CASO AMBÍGUO / FEATURE ABERTA
                                ↓                                        ↓
             Ingresso Direto no Workflow Canônico:              @prompt-structuring (R-041)

             - WORKFLOW-GOVERNANCE (→ @agent-auditor)                    ↓
             - WORKFLOW-PROMPT-SYNTHESIS (→ @prompt-structuring)         ↓
                                ├────────────────────────────────────────┘
                                ↓
                 [EXECUÇÃO SEQUENCIAL ESTRITA (R-050)]
                 - WORKFLOW-BUG-FIX: triage → red-test → bug-fixer → green-test → gate & quality review loop (R-050.4)
                 - WORKFLOW-REFACTORING: rules → graph/blast radius → plan → batch-exec → validation & quality review loop (R-050.4)
                 - WORKFLOW-TECHNICAL-ANALYSIS: scope → deterministic analysis → report
                 - WORKFLOW-FEATURE-DEVELOPMENT: requirements → blueprint → test-strategy → TDD → duplo gate & quality review loop (R-050.4)

                 - WORKFLOW-DEPENDENCY-VULNERABILITY-REMEDIATION: scan → blast-radius → bump → adapt → quality gate & quality review loop (R-050.4)

                                ↓

**Fases de Execução:**

1. **Triagem & Seleção de Workflow** (agent-router): classificar intenção, acionar Fast-Path ou Prompt Structuring e declarar `Agente Ativo` e `Workflow` (R-050)
2. **Execução de Workflow** (agents especialistas): seguir os estados do pipeline determinístico em `task_mode`
3. **Re-triagem por turno** (R-042): a cada nova mensagem, o agent ativo checa deriva de intenção contra seu Não-Escopo antes de responder; ao detectar deriva, devolve controle ao `@agent-router` via handoff (nunca prossegue fora do escopo)
4. **Validação & Não-Regressão** (self-check / tests): executar verificação de qualidade e suites de teste (R-046)
5. **Resumo & Handoff Contínuo** (R-028, R-047): reportar resultado, evidências e acionar próximo agente ou aprovação humana

### Checklist de Genericidade (R-038)

**ANTES de submeter arquivo novo em `.github/` (agents, skills, prompts, copilot-instructions):**

- [ ] Substitua mentalmente todos os nomes de projeto por `[PROJETO]` — o texto faz sentido?
- [ ] Substitua todas as tecnologias/frameworks por `[TECH]` — o texto ainda é válido?
- [ ] Nenhuma referência a: domínio de negócio, linguagem de programação específica, framework exclusivo
- [ ] Se há customização de tech/domínio, está em `.github/instructions/*.instructions.md` (adapter)?
- [ ] Se há lista de exemplos concretos, apontam para `.github/instructions/README.md` e nunca duplicam?

**Teste rápido**: Seu documento continua útil para um projeto completamente diferente (ex: Go backend, React frontend)?
- ✅ Sim? → Pode ir para `.github/` (global)
- ❌ Não? → Deve ir para `.github/instructions/<adapter>.instructions.md` (adapter)

### Checklist de Anonimização de Evidência Real (R-044)

**ANTES de persistir qualquer changelog, seção de validação ou exemplo derivado de análise de repositório real** (aplica-se sobretudo a agents analíticos: `code-knowledge-graph`, `business-rules-extractor`, `context-builder`, `project-scanner`):

- [ ] Nomes de repositório/projeto genericizados (`[PROJETO-A]`, `[PROJETO-B]`, ...)?
- [ ] Nomes de classe/método/variável reais trocados por equivalentes de exemplo (`ServicoExemploX`, `operacaoExemploX`)?
- [ ] Pacotes/namespaces/domínios reais (`com.empresa.*`, URLs reais) trocados por `com.exemplo.*`/`http://contrato.exemplo.com/...`?
- [ ] Caminhos absolutos de sistema de arquivos (`C:\Users\...`, `D:\workspace\...`, `/home/...`) removidos ou trocados por placeholder (`<workspace>\[PROJETO-X]`)?
- [ ] Nome de empresa/ecossistema real removido ou genericizado?
- [ ] Métricas numéricas agregadas (contagens, %) — **podem permanecer reais**, não identificam projeto.

**Teste rápido**: um terceiro lendo o arquivo commitado consegue inferir qual projeto/empresa foi analisado?
- ✅ Não consegue? → Pode commitar.
- ❌ Consegue? → Genericize antes de commitar (bloqueante, mesma severidade de R-038).
